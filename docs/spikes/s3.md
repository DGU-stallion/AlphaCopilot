## 验证目标

Python MCP server（官方 `mcp` 包 / FastMCP）经 stdio 被 dsh 拉起、完成

## 最终 patch 行形态

`~/.dsh/profiles/alphacopilot/cordis.patch.yml`：

```yaml
- insert:
    - id: mcp-alphacopilot-research
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: alphacopilot-research
        transport: stdio
        command: <s3venv>/bin/python
        args: ['-m', 'alphacopilot_research.server']
        env: {}
        failOnStartupError: false
```

**坑 1（修正侦察假设）**：patch entry 不是裸 loader 行，必须包 `- insert:`。
裸写 `- id: ...` 报 `patch: entry "mcp-alphacopilot-research" not found`
（patch 层把首字段当目标 id 做覆盖/禁用）。与 S1 结论一致，本次再证实。
**坑 2**：原文件占位符 `[]` 必须删掉，否则追加后 YAML 解析失败。

工具公开名：`mcp__alphacopilot-research__get_quote` /
`mcp__alphacopilot-research__get_kline`。无额外 trust 门禁。

## 坑与选型结论

1. **mcp SDK 版本**：2.x 把 FastMCP 改名 MCPServer 且 API 变动大，
   pyproject 固化 `"mcp>=1.9,<2"`；1.x 里 `mcp.tool()` 是装饰器工厂，
   编程式注册须写 `mcp.tool()(fn)` 而非 `mcp.tool(fn)`。
2. **stdio vs http 选型建议**：spike 维持 **stdio**。理由：
   - dsh-mcp-client 原生支持 stdio entry，零额外基础设施；
   - 数据层是纯函数库 + requests，无状态、随 profile 生命周期启停即可；
   - http/SSE 只有在多客户端共享长连缓存或跨机部署时才有收益，
     T08 若上 REST 面（README 已预留）可另起 uvicorn，MCP 面仍走 stdio。
3. **mootdx 与 asyncio 冲突（遗留）**：装了 mootdx 后 get_kline 在 MCP
   事件循环内触发其内部 proxy verify 的 asyncio 任务风暴，最终
   `ValueError: not enough values to unpack`；且 mootdx 钉死
   `httpx<0.26`，与 mcp 要求的 `>=0.27.1` 冲突。建议 T08 的 K 线改走
   东财 HTTP 接口，或用 `asyncio.to_thread` 包 mootdx 并隔离 venv。
4. sys.path 注入 backend/ 是 spike 权宜（server.py 有 TODO），T08 改为
   正常依赖声明。
