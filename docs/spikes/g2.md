## 跨进程续传的精确诊断（不是笼统 FAIL）

分两个对照实验定位缺口：

1. **持久化成立**：第一轮后 `session.jsonl` 有 17 行，含 `user/message` 与 assistant 事件
   —— 历史确实落盘。
2. **同进程 session 内记忆成立**：另做对照实验，同一 runtime 进程、同 session_id 连发两轮，
   mock 收到的 messages 条数 `2 → 4`（第二轮带上了第一轮历史）。**session 内记忆通。**
3. **跨进程加载不成立**：关闭第一个 runtime、用同 session_root + 同 session_id 新起第二个
   runtime 发 prompt，mock **第二轮根本没被调用**（`final_response=''`）。
   → 新 runtime 不会自动加载磁盘上已有的 session.jsonl 到内存。

**根因**：dsh 的会话是 event-sourced 的**内存**模型（`docs/subsystems/session.md`：
"LLM message history is derived from the log"）；持久化后端有 cold-session
`load/inspect/prepare` 能力（`persistence.md`），但 **SDK 的 `Session.run` 对已有
session_id 默认不触发跨进程 resume**。跨进程恢复需要显式机制。

### 精确失败模式（iteration 2 追加实测）

进一步捕获第二进程的 `finish_reason` 与 notifications，得到 dsh 的**确切行为**：

```
轮1 finish=completed final='答复'
轮2 finish=error  final=''
轮2 error: turn/end reason.kind=error,
  message='session "dur" already has a persisted log on disk that does not
           match this live session (id collision)'
```

即：新 runtime 对同 session_id 发 prompt 时，dsh **主动检测到磁盘已有同 id 的 log 并
拒绝**（id 冲突保护，防止两个 live session 覆盖同一磁盘 log）。不是静默丢历史。

代码路径已定位：`packages/sdk/server/src/server.ts` 的 `createSession()` 直接
`ctx.agents.create({ sessionId })`，**不调 persistence 的 `prepare/inspect`**，
所以 SDK 高层 API 无法触发跨进程 adopt。

## 对架构的指导（写回 PLAN/ADR）

这个结论**正面印证了 ADR-0006 的核心决策**，不是障碍：

- **产品真源在我们自己的 DB，前端不读 dsh JSONL** —— 因此历史续传本就该由业务层负责：
  我们存每条 message，重启/刷新后从**自己的 DB** 重建对话，而不是依赖 dsh 跨进程恢复。
- **对 T27（dsh 适配层）的直接约束**：一会话一子进程，进程存活期间 session 内记忆可用；
  进程结束后，续聊 = 业务层把历史作为新 prompt 的上下文重新喂入（或后续探索 dsh 的
  cold-session `prepare` 显式恢复，作为 T27 的可选优化，非必需）。
- **硬约束（iteration 2 实测确认）**：**每次新起 runtime 必须用全新 session_id**。
  复用磁盘上已存在的 session_id 会被 dsh 以 "id collision" 拒绝（turn/end error）。
  因此 T27 的会话映射应为：我们 DB 里的「对话」↔ 每次进程运行分配一个**新** dsh session_id，
  对话历史由业务层从自己的 DB 重建后喂入，绝不复用旧 dsh session_id。
- **"停止"能力**：靠杀子进程实现，已验证可行；配合"重活外移到 job"，中途取消的缺陷被抵消。

## 未尽事项（留给 T27，非门禁阻塞）
