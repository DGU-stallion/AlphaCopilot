候选 1：三重入口点（三具 FastAPI 尸体）

Strong
backend/app.py backend/research/app.py backend/quant/api_server.py backend/quant/router.py

问题

系统存在三个可独立启动的 FastAPI 应用：统一入口 app.py、Research 独立入口 research/app.py、Quant 独立入口 quant/api_server.py。三者各自实现 CORS 配置、auth 中间件、生命周期钩子。统一入口又通过 quant/router.py 适配层选择性地导入 Quant 路由，形成第四层间接——每层都有自己的 try/except 降级逻辑。

这三个入口的接口几乎一样大（CORS + auth + route mounting + lifecycle），但各自的实现差异极小——它们是典型的浅模块。修改认证策略需要同步改三处。测试时搞不清该启动哪个 app。

方案

删除 research/app.py 和 quant/api_server.py 作为可执行入口（保留 router 适配）。将中间件、auth、CORS 集中到 app.py 一处。Research 和 Quant 各自只暴露一个 create_router() -> APIRouter——纯路由，无应用级副作用。

收益

  • Locality：auth/CORS/lifecycle 集中一处，改一次生效全局
  • Leverage：测试只需一个 TestClient(app)，无歧义
  • 测试改善：集成测试针对统一 app 写，不再有"研究端口 vs 量化端口"的混淆

候选 2：Quant 模块的 sys.path 黑魔法与幽灵 src. 前缀

Strong
backend/quant/router.py backend/quant/agent/__init__.py backend/quant/agent/loop.py backend/quant/tests/conftest.py

问题

Quant 模块从上游 Vibe-Trading 继承了一套 from src.agent.*、from src.tools.*、from backtest.* 的 import 约定——但实际目录名是 agent/、tools/、backtest/，根本没有 src/ 目录。它靠 sys.path.insert(0, quant_dir) 在运行时 hack 路径解析，且多处重复这个 hack（router.py、conftest.py、mcp_server.py）。

这违反了locality：理解 from src.agent.loop import AgentLoop 需要知道一个不可见的运行时条件（sys.path 被修改过）。IDE 类型检查和 AI 代码导航全部失效。接缝泄漏严重——一个不相关目录下的 src/__init__.py 可能被意外解析到（实际已发生：毕业论文目录下的 src 包被命中）。

方案

将 Quant 模块重组为标准 Python 包结构。两个选项：(a) 在 quant/ 下真正创建 src/ 目录作为命名空间包，或 (b) 全局替换 from src.X 为相对导入 from quant.X，配合 pyproject.toml 声明 packages = ["quant"]。删除所有 sys.path.insert hack。

收益

  • Locality：import 语句自解释，无需运行时上下文
  • Leverage：IDE 类型检查恢复；mypy/pyright 能静态分析跨模块依赖
  • 测试改善：conftest 不再需要 path hack，pytest 自然发现测试

Before — 幽灵路径

  agent/loop.py → from src.agent.tools import ...
  router.py → sys.path.insert(0, quant_dir)
  tests/conftest.py → sys.path.insert(0, AGENT_DIR)

候选 3：投研 Router 单文件巨函数

Worth exploring
backend/research/router.py

问题

create_research_router() 是一个将所有路由端点（聊天、持仓、行情、资讯、个股数据、自选股、研报）定义在同一个函数内的巨型闭包。所有端点共享模块级缓存（_PCT_CACHE、_ANN_CACHE）、工具函数（_validate、_cached）、Pydantic model。

这个模块的接口是好的（一个函数返回 APIRouter），但其实现缺乏内部接缝——不同业务域（持仓管理、市场数据、聊天）混在同一个作用域。要单独测试「持仓 API」必须导入整个研究模块。缓存是模块级副作用，无法在测试间隔离。

方案

将 create_research_router() 拆为 3-4 个内部子模块，每个负责一个业务域（chat、portfolio、market_data、reports），各自暴露 register_xxx_routes(router)。模块级缓存替换为传入的缓存对象（测试时注入 fake）。外部接口不变——create_research_router() 仍然是唯一的对外接缝。

收益

  • Locality：持仓 bug 只需看 portfolio 子模块，不需扫全文件
  • Leverage：外部接口不变（deletion test 通过），内部获得可测试的接缝
  • 测试改善：可单独测试持仓逻辑，注入 mock 缓存，无网络副作用

候选 4：Quant Router 的"优雅降级"——实际是接缝泄漏

Worth exploring
backend/quant/router.py backend/app.py

问题

create_quant_router() 为每个路由组（sessions、runs、swarm、alpha、settings、auth、system）分别 try/except，把失败的依赖收集到 _missing_deps 列表，最后注册一个 catch-all 503 fallback。这意味着：

  • 接缝在运行时才确定形状——同一个 router 对象在不同机器上注册不同数量的路由
  • 测试无法预测 router 的行为（取决于哪些 import 成功）
  • 503 catch-all fallback 掩盖真正的配置问题——用户看到"部分不可用"但不知道为什么
  • app.py 自己也有一层 try/except 包裹整个 quant router，形成双重降级

方案

Fail fast at startup：将依赖检查提前到应用启动阶段（preflight check），如果核心依赖缺失则启动失败并报明确错误。对真正可选的路由组（如 alpha 因子分析），使用显式 feature flag（环境变量）控制是否注册，而非靠 import 是否成功。删除 catch-all fallback。

收益

  • Locality：router 形状在启动时确定且不可变，行为可预测
  • Leverage：测试可断言"这些路由一定存在"，无需处理 503 分支
  • 测试改善：集成测试不会因为缺少 optional dep 而静默跳过路由覆盖

候选 5：Agent Loop 配置耦合——深度被配置分散稀释

Speculative
backend/quant/agent/loop.py backend/quant/config/

问题

AgentLoop 本身是一个深模块（大量 context management、streaming、batching 逻辑藏在 run() 方法后面），但它的深度被一系列 get_env_config() 调用稀释了。Loop 的每个可调参数（token_threshold、heartbeat_interval、stream_retry_delay、tool_timeout、goal_max_continuations）都通过 lazy from src.config.accessor import get_env_config 在函数级别获取。

这导致：(1) 测试要 monkeypatch 5 个不同的模块级函数；(2) 配置变更的影响面不可见——改一个 yaml 字段可能影响 AgentLoop 的 5 个行为维度；(3) _override() 机制用 sys.modules[__name__].__dict__ 做猴子补丁，进一步降低可读性。

方案

引入一个 AgentTuning dataclass（frozen），在 AgentLoop 构造时一次性传入。测试直接构造 AgentTuning(token_threshold=100, ...)，不需要 monkeypatch。Loop 内部不再访问全局配置。

收益

  • Locality：所有调参集中在一个 dataclass 定义中，而非散布在函数间
  • Leverage：AgentLoop 接口更小——构造参数替代隐式全局状态
  • 测试改善：无需 monkeypatch；直接传不同 tuning 实例测试边界行为

Before — 散布配置访问

class AgentLoop:
  def run(...):
    threshold = _token_threshold()  # → get_env_config()
    interval = _heartbeat_interval_s()  # → get_env_config()
    retry = _stream_retry_delay_s()  # → get_env_config()
    timeout = _tool_timeout_seconds()  # → get_env_config()
    max_cont = _goal_max_continuations()  # → get_env_config()
    # 5个隐式全局依赖，测试需 5 个 monkeypatch

After — 显式注入

@dataclass(frozen=True)
class AgentTuning:
  token_threshold: int = 128_000
  heartbeat_interval_s: float = 30.0
  stream_retry_delay_s: float = 1.0
  tool_timeout_s: float = 120.0
  goal_max_continuations: int = 5

class AgentLoop:
  def __init__(self, ..., tuning: AgentTuning): ...
  # 测试: AgentLoop(tuning=AgentTuning(token_threshold=100))

🎯 首选推荐

候选 2（sys.path 幽灵导入）是我建议首先解决的。原因：

  1. 它是其他所有改进的前提。在 import 路径不稳定的情况下，任何重构（拆分 router、统一入口、提取 AgentTuning）都会触发大量不可预测的 import 失败。先修正包结构，后续变更才有稳定的基础。
  2. 风险最低。这是纯 rename + 正则替换——行为不变，只改 import 路径。配合一次性 sed 脚本和 pytest 全量跑通即可验证。
  3. 即刻收益最大。修正后 IDE 类型检查恢复、AI 代码导航恢复、测试发现恢复。这三项对日常开发摩擦的消除是立竿见影的。

修正 import 后，候选 1（统一入口） 自然成为第二步——因为 research/app.py 和 quant/api_server.py 可以简化为开发时的 convenience script（不含任何中间件逻辑）而非独立应用。
